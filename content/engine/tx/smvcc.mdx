# Simulated MVCC <Tag description={"v26.1+"} />

Simulated MVCC gives a Soft Transaction read-your-writes behavior while its
mutations are deferred. It is a transaction-local overlay, not a replacement
for source isolation or a shared database snapshot.

## Activation

Simulated MVCC is active only when all of these conditions are true:

- Soft Transactions are enabled for the data source
- the strategy is `DEFER_OPERATION`
- `mvcc.enabled` is `true`
- the query runs inside an active transaction

With `IMMEDIATE_OPERATION`, reads use the state exposed by the data source and
simulated MVCC is not applied.

<Callout type="info">
  A provider that advertises native transactions owns read visibility through
  its bound provider connection. Kubling does not add the simulated MVCC overlay
  to that path, even if `mvcc.enabled` appears in the data-source configuration.
</Callout>

## Read-your-writes behavior

For a deferred mutation, Kubling records the logical effect under the active
transaction:

- `INSERT` adds a transaction-local row
- `UPDATE` replaces the transaction-local version of the row
- `DELETE` hides the row with a transaction-local tombstone

A subsequent `SELECT` reads the source and merges that result with the active
transaction's changes. Other transactions do not see this overlay.

Simulated MVCC does not provide:

- isolation between concurrent transactions
- a source-wide snapshot
- durable storage for application data
- process-restart recovery of the transaction-local view

[Row locking](/engine/tx/rowlocking) remains responsible for conflicting writes,
and [recovery](/engine/tx/recovery) handles durable transaction outcomes.

## Configuration

```yaml
softTransactions:
  enabled: true
  strategy: DEFER_OPERATION
  mvcc:
    enabled: true
    dbBasePath: "/var/lib/kubling/mvcc"
```

The configuration belongs to the data source. Use a path owned by that Kubling
instance and backed by storage with enough capacity for the active transaction
workload.
