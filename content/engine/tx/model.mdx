# Soft Transaction model

A Soft Transaction is Kubling's emulation path for a data source that cannot
provide the native transaction semantics required by the workload. It is
configured per data source, so one client transaction can contain native and
emulated participants.

<Callout type="warning">
  A Soft Transaction cannot turn compensation into atomic rollback. Use it only
  when the external effects are reversible and the application accepts the
  documented failure boundaries.
</Callout>

## Strategies

| Strategy | When the mutation reaches the source | Rollback behavior |
| --- | --- | --- |
| `DEFER_OPERATION` | During transaction completion | Discards work that has not executed; compensates an applied prefix if completion fails. |
| `IMMEDIATE_OPERATION` | When the statement runs | Compensates mutations that were already applied. |

`DEFER_OPERATION` is the default. A VDB can use different strategies for
different data sources in the same transaction.

## Lifecycle

### Begin

Kubling creates the transaction context. A data source becomes a participant
when the transaction first uses it.

### Execute

For each emulated participant, Kubling records mutations in statement order.
Depending on the strategy, it either retains the mutation for completion or
executes it and durably records the information needed for compensation.

### Complete

On commit, deferred mutations are applied and immediate mutations are accepted
as the transaction outcome. On rollback, unapplied work is discarded and
already applied work is compensated in reverse order.

Locks and transaction-local state are released only after commit, rollback or
timeout completes. A failed compensation is reported as a failed rollback and
its recovery evidence is retained.

## Native provider selection

For a provider-backed data source, `softTransactions.enabled` opts the source
into coordinated transactions. Kubling then selects the strongest path the
provider declares:

- A provider with native transactions owns isolation, statement execution,
  commit and rollback.
- A provider without native transactions uses the configured Soft Transaction
  strategy.

When the native path is selected, `strategy` and `mvcc` do not override the
provider's transaction model. Kubling also does not add emulated row locks,
simulated MVCC or compensation.

## Multi-request mutations <Tag description={"v26.7+"} />

A provider may be able to mutate one exact row but be unable to encode several
resolved rows in one request. Kubling can split that statement only when an
explicit transaction provides a safe rollback boundary:

- a provider-native transaction executes every request on the bound provider
  connection and marks the transaction rollback-only if one fails
- a Soft Transaction acquires the complete lock set and records every mutation
  and compensation before the first request can execute

Without either boundary, Kubling rejects the statement before sending the first
mutation. Providers that can represent the complete exact filter continue to
receive one request.

See [Commit, rollback and compensation](/engine/tx/finalization) for finalization
semantics and [Timeouts and recovery](/engine/tx/recovery) for process-restart
behavior.
