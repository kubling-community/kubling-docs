# Transactions

Kubling coordinates client transactions across the data sources used by a VDB.
The guarantee for each participant depends on whether the underlying system can
own a native transaction or Kubling must emulate rollback through a Soft
Transaction.

## Transaction paths

| Participant path | Isolation and rollback owner | Behavior after a Kubling restart |
| --- | --- | --- |
| Database data source using native transactions | The database | A prepared transaction can be recovered when recovery is enabled and the source supports the recovery contract. |
| gRPC provider with native transactions | The provider and its native system | A prepared branch can be recovered only when the provider also advertises durable recovery and a stable resource identity. |
| Soft Transaction | Kubling coordinates row locks, optional transaction-local visibility and compensation | Kubling can resume a known rollback from its journal. It refuses to guess when the external outcome is ambiguous. |

Kubling never treats live transaction support as proof that a participant can
recover after a process restart. Recovery is enabled separately and requires a
durable participant on both sides of the transaction boundary.

## Native transactions

Native participants retain their own isolation, conflict handling and commit or
rollback semantics. Kubling keeps the same participant enlisted until the
transaction commits, rolls back or times out.

For a provider-backed data source, `softTransactions.enabled` enrolls the source
in the coordinated transaction. When the provider advertises native transaction
support, Kubling uses that path and does not add its own row locks, simulated
MVCC or compensation. The configured Soft Transaction strategy remains relevant
only when the provider does not offer native transactions. Reads and mutations
share the provider connection bound to the transaction; statement failures and
affected-row counts are available when the statement executes, while commit and
rollback remain controlled by the surrounding transaction.

<Callout type="info">
  Native transaction support and durable recovery are separate capabilities. A
  provider may safely commit and roll back while its connection is alive but be
  unable to recover a prepared branch after either process restarts.
</Callout>

## Soft Transactions

Use a Soft Transaction when a data source cannot provide the native transaction
semantics required by the workload. Kubling can then:

- defer mutations until commit or execute them immediately
- acquire deterministic row locks for conflicting writes
- provide transaction-local read-your-writes behavior when simulated MVCC is enabled
- generate compensation for effects that cannot be rolled back natively

Compensation is a corrective action, not database rollback. It can fail, and it
cannot make an irreversible external effect disappear. Applications must decide
whether the affected system and mutation are suitable for this model.

## Boundaries

- A transaction is only as recoverable as every participant it contains.
- Recovery is disabled by default for database and provider-native participants.
- An in-memory participant cannot preserve prepared work across a restart.
- A client timeout does not prove that the transaction committed or rolled back.
- Kubling fails closed when it cannot determine whether a Soft Transaction side
  effect occurred.

See [Soft Transaction model](/engine/tx/model) for emulated execution semantics
and [Timeouts and recovery](/engine/tx/recovery) for configuration, supported
participants and operating procedures.
