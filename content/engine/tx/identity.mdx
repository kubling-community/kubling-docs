# Row identity

Kubling needs a stable row identity when it must lock a row, maintain a
transaction-local version or generate a precise compensation. The identity is
derived from table metadata and remains stable for the active VDB.

## When identity is required

Row identity is required for data sources using Kubling's Soft Transaction
emulation. It can also be required when Kubling must resolve an `UPDATE` or
`DELETE` into exact per-row provider requests.

<Callout type="info">
  A provider that advertises native transactions owns its locking and isolation.
  Its tables do not need a key solely for Kubling transaction bookkeeping.
  However, a usable key is still required if a mutation cannot be represented as
  one exact provider request and must use the per-row fallback.
</Callout>

## Usable keys

Kubling selects a primary key or unique key whose complete column set is usable:

- every key column is `NOT NULL`
- no key column uses the `exclude_from_row_identity` directive
- all key values are available when the row identity is needed

If one column is excluded, Kubling discards that complete key rather than using
only part of it. Another primary or unique key can still satisfy the requirement.

For a data source using Soft Transactions, Kubling validates this metadata when
the VDB is loaded. The VDB is rejected when a table that requires identity has no
usable key.

## Inserts

An `INSERT` can establish row identity in two ways:

- The statement supplies every identity value.
- The data source generates the identity and can return the generated value.

Deferred execution requires the identity before the mutation reaches the data
source. A generated identity therefore requires immediate execution and a data
source that can return generated values.

Provider-native transactions do not require generated-value support merely to
execute the `INSERT`. The statement can still report its affected-row count;
applications that need the generated value must use a provider that advertises
that capability.

## Updates and deletes

When a mutation needs Kubling-managed row identity, Kubling first resolves the
affected rows and then:

1. reads every identity column
2. derives the row identities
3. acquires the complete lock set when Soft Transaction locking applies
4. prepares the exact mutation and compensation work

If the complete identity or lock set cannot be obtained, the mutation fails
before external writes begin.

## Checklist

- Define a primary or unique key for every table that uses Soft Transaction
  emulation.
- Mark every identity column `NOT NULL`.
- Keep identity values available to mutation projections.
- Use `exclude_from_row_identity` only when another complete key remains.
- Verify generated-value support before relying on a source-generated key.

See [Row locking](/engine/tx/rowlocking) for conflict behavior and
[Soft Transaction model](/engine/tx/model) for strategy selection.
