# Row locking

Kubling uses row locks to prevent conflicting mutations when it owns the Soft
Transaction behavior for a data source. Locks are derived from the stable row
identity described in [Row identity](/engine/tx/identity).

## Scope

A lock is scoped to the data source, row identity and owning execution context.
Kubling acquires the required locks before it registers or executes a
mutation. If a lock is unavailable, the operation fails before external writes
begin.

When Soft Transactions are enabled for an emulated participant, this protection
also applies to mutation paths outside an explicit client transaction. This
prevents a non-transactional write from bypassing an active Soft Transaction's
lock.

## Lifetime

Inside a transaction, locks remain owned by the same participant until the
transaction commits, rolls back or times out. Kubling releases them after the
terminal path completes, including compensation where required.

If a crash leaves a Soft Transaction outcome unresolved, its durable row locks
are retained. Kubling does not release them and continue with an uncertain
external state. See [Timeouts and recovery](/engine/tx/recovery).

## Conflict behavior

When another execution already owns one of the required rows:

- Kubling rejects the new mutation
- no external mutation request is sent

There is no table-level lock escalation. Large multi-row mutations can therefore
claim many row locks and should be bounded by application predicates.

<Callout type="info">
  Kubling does not add this lock layer when a provider advertises native
  transactions. The provider and its native system own isolation and conflict
  handling for that path.
</Callout>
