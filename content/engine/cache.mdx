# Query result cache <Tag description={"v24.5.3+"} />

Kubling can cache eligible `SELECT` results so a repeated request does not need
to read the source again. Caching is configured at three levels:

1. application settings define scope, capacity and manual invalidation
2. a Data Source enables result caching and sets its default TTL
3. schema and table policies decide which tables are eligible

The cache is local to one Kubling process. It is not a copy of the source and
does not provide cross-instance consistency.

<Callout type="warning">
  Enable result caching only when its freshness policy is explicit. Changes
  made directly in a remote system are invisible to Kubling until the entry
  expires or an external process invalidates it.
</Callout>

## Enable caching for a Data Source

`cache.enabled` turns result caching on for the Data Source. The schema default
then decides which imported tables participate:

```yaml copy
- name: "inventory"
  dataSourceType: "PROVIDER_GRPC"
  configObject:
    address: "inventory-provider"
    port: 50051
    cache:
      enabled: true
      ttlSeconds: 43200
  schema:
    type: "PHYSICAL"
    cacheDefaultStrategy: "CACHE"
```

`cache.enabled` defaults to `false`. `cacheDefaultStrategy` defaults to
`CACHE`, but it has no effect until result caching is enabled for the Data
Source.

### Schema and table policy

Use the `cache` table option to override the schema default:

```sql copy
CREATE FOREIGN TABLE EVENT (
    id string NOT NULL,
    payload json,
    PRIMARY KEY (id)
)
OPTIONS (
    cache 'enabled',
    cache_ttl '60'
);
```

Policy values are case-insensitive. Their resolution is:

| `cacheDefaultStrategy` | Table `cache` option | Cache the table? |
| --- | --- | --- |
| `CACHE` | omitted, `enabled` or `schemaDefault` | Yes |
| `CACHE` | `disabled` | No |
| `NO_CACHE` | `enabled` | Yes |
| `NO_CACHE` | omitted, `disabled` or `schemaDefault` | No |

## Time to live

`cache.ttlSeconds` sets the Data Source default in seconds. Its default is
`43200` (12 hours). A table can override it with `cache_ttl`.

Both values must be non-negative:

- `0` prevents the result from being stored
- replacing an entry starts a new complete TTL
- reading an entry does not extend its freshness window
- malformed, negative or overflowing values fail before the VDB becomes
  available

## Application scope and capacity

Application settings apply independently to each backing Engine cache,
including result and prepared-plan caches:

```yaml copy
cache:
  sessionScoped: false
  maxEntries: 1024
  # Optional logical-result limit for each Engine cache.
  maxMemorySizeMB: 256
  enableInvalidateEndpoint: false
```

| Property | Behavior |
| --- | --- |
| `sessionScoped` | Keeps eligible result entries within the originating session when `true`; default `false` |
| `maxEntries` | Maximum entries in each Engine cache; default `1024` and must be non-negative |
| `maxMemorySizeMB` | Optional estimated logical-result volume limit, in MiB, for each Engine cache |
| `enableInvalidateEndpoint` | Enables the manual invalidation HTTP endpoints; default `false` |

### Logical size limit <Tag description={"v26.7+"} />

`maxEntries` remains active when `maxMemorySizeMB` is set. The size limit does
not replace the entry limit.

To estimate a cached result, Kubling samples at most 100 rows and projects the
sampled payload across the complete result row count. Entries that do not have
a usable result-size estimate still receive a non-zero capacity charge.

<Callout type="info">
  `maxMemorySizeMB` bounds estimated logical result volume. It is not a JVM
  heap limit and it does not include storage owned by the
  [Buffer Manager](/engine/buffer-manager). Size estimation also adds work when
  an entry is stored.
</Callout>

## Invalidation

Updates executed through Kubling invalidate cached results associated with the
resolved table. SQL aliases do not change that association.

Changes performed outside Kubling require TTL expiry or manual invalidation.
Enable the endpoints with `cache.enableInvalidateEndpoint: true`, then choose
the required scope:

```http
DELETE /api/v1/cache/vdb/{vdb}/table/{table}
DELETE /api/v1/cache/table/{table}
```

The first endpoint targets one VDB name. The second targets every deployed
VDB. `{table}` may be a qualified `schema.table` name or an unqualified table
name:

- a qualified name targets that table in one schema
- an unqualified name targets matching tables in the selected VDB scope
- matching is normalized and case-insensitive

For example:

```bash copy
curl --include --request DELETE \
  "https://kubling.example.com/api/v1/cache/vdb/InventoryVDB/table/inventory.EVENT"
```

A successful request returns an empty `200` response and the number of removed
result entries in this header:

```http
Kubling-Cache-Invalidated-Entries: 3
```

The endpoints invalidate result entries only; they do not clear prepared
plans. When disabled, the endpoints return `404`.

<Callout type="warning">
  Enabling manual invalidation adds state-changing endpoints to the HTTP
  interface. Restrict them at the ingress or reverse proxy and expose them only
  to trusted automation.
</Callout>

### Multiple Kubling instances

Invalidation and cache contents are process-local. If several Kubling
instances can serve the same VDB, send the invalidation to every instance or
use a TTL that tolerates independent expiry. Kubling does not broadcast cache
invalidation between instances.

## Observe cache behavior

Use the [cache metrics](/observability/metrics#cache-metrics) to distinguish
hits, misses, logical result size, charged capacity and removal causes for each
backing cache.

| Symptom | Check |
| --- | --- |
| An entry is never retained | Check for TTL `0`, `maxEntries: 0` or immediate capacity pressure |
| VDB activation fails | Check table `cache` values and Data Source or table TTLs |
| Frequent `cause=size` removals | Compare current entries and logical size with both configured limits |
| Frequent `cause=expired` removals | Confirm that the TTL matches the required freshness window |
| Stale results differ between instances | Confirm that invalidation reached every Kubling process |

The complete application and Data Source field definitions are available in
the [configuration schemas](/schemas).
